# 对抗性审查（Adversarial Review）

## 核心假设

已知的失败模式比未知的漏洞更容易找到。先根据调用链特征生成一批**系统稳定性失败假设**，然后有目的地验证每一个假设。

每轮只深入调查一个或少数几个假设，不做全面扫描。

## 假设库

根据项目特征从 10 个类别中选取最相关的 5-10 个假设：调用契约、边界输入、状态机、异步链路、一致性、幂等性、错误传播、生命周期、配置边界、兼容性。

> 完整假设列表和选取原则，读 `references/hypothesis-library.md`。

## 结论等级

| 等级 | 含义 |
|------|------|
| `HYPOTHESIS` | 仅是假设，来自经验或常见失败模式，尚未查代码 |
| `INVESTIGATING` | 正在调查 |
| `SUSPICIOUS` | 有局部迹象，但证据不足以确认 |
| `CONFIRMED` | 有代码路径、触发条件和失败后果 |
| `DISPROVED` | 已找到反证，假设不成立 |
| `BLOCKED` | 需要运行环境、数据、日志或人工确认 |

**`CONFIRMED` 的硬性证据门槛（必须同时满足）：**

1. 已读取真实代码文件，不是推断或"典型模式"示例
2. 能指出具体文件路径和行号（或函数名）
3. 能描述触发条件：什么输入/调用序列会触发这个问题
4. 能描述失败后果：触发后系统会发生什么

**不满足以上任一条件，只能标 `SUSPICIOUS`，不能标 `CONFIRMED`。**

"这是遗留代码的典型模式"不是证据。"高概率存在"不是证据。只有读到真实代码并能指出路径，才是证据。

## 工作流程

### 第一步：了解调用链上下文

如果配合宏观审查使用，读取：
- `review-log/STATE.md`（当前链条和状态）
- `review-log/chains/<current-chain>.md`（节点列表和已知契约）

如果独立使用，快速扫描项目结构了解：技术栈、外部边界、数据流向、异步机制。

### 第二步：生成假设列表

根据调用链特征，从假设库中选取最相关的 5-10 个假设，标注初始等级为 `HYPOTHESIS`。

**选取原则：**
- 优先选与当前链条直接相关的假设
- 优先选遗留代码或近期重构区域的假设
- 不要全选，聚焦最可能的失败点

### 第三步：针对每个假设执行定向调查

对每个假设：
1. 定位目标：找到最可能出现该问题的代码位置
2. 验证假设：检查是否存在假设描述的问题
3. 更新结论等级

**调查深度原则：**
- `CONFIRMED` → 记录具体位置、触发条件、失败后果，停止深挖
- `DISPROVED` → 简短记录反证，继续下一个假设
- `SUSPICIOUS` → 记录局部迹象，标记为需进一步调查
- `BLOCKED` → 标记阻塞原因，继续下一个假设

### 第四步：输出审查报告

```markdown
# 对抗性审查报告

## 项目：<项目名>
## 审查日期：<日期>
## 审查范围：<当前关键链或模块>

## 假设与结论

| 假设ID | 描述 | 结论等级 | 位置 |
|-------|------|---------|------|
| CONTRACT-02 | 返回值结构不一致 | CONFIRMED | src/services/auth.ts:45 |
| ASYNC-02 | 异步错误未捕获 | SUSPICIOUS | src/controllers/user.ts |
| STATE-01 | 非法状态转换 | DISPROVED | 有前置校验 |

## 已确认问题

### CONTRACT-02：返回值结构不一致
**位置：** `src/services/auth.ts:45`
**触发条件：** 用户不存在时返回 null，但调用方期望抛出异常
**失败后果：** controller 未处理 null，直接访问 null.id 导致崩溃
**建议：** 统一为抛出 UserNotFoundError

## 可疑问题（需进一步调查）

### ASYNC-02：异步错误未捕获
**位置：** `src/controllers/user.ts`
**迹象：** 发现 Promise 链未加 .catch()，但未确认是否有全局捕获
**建议：** 人工确认全局错误处理是否覆盖此路径

## 已排除假设

- STATE-01：`src/services/order.ts:12` 有明确的状态前置校验

## 总结

本次审查覆盖 <N> 个假设，确认 <M> 个问题，<K> 个可疑，<J> 个已排除。
```

### 第五步：回写宏观审查状态（如配合使用）

把 `CONFIRMED` 问题写入 `review-log/evidence/<task-id>.md`，更新 `review-log/QUEUE.md` 中对应任务状态。

## 常见错误

- 把所有假设都跑一遍 → 根据项目特征筛选 5-10 个最相关的
- 把 SUSPICIOUS 写成 CONFIRMED → 严格区分，有代码路径才能 CONFIRMED
- 假设成立后继续深挖所有细节 → 记录位置和触发条件，移交人工或下一轮
- 独立运行时忽略调用链上下文 → 先了解链条结构再提假设
